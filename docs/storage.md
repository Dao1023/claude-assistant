# 存储选型:JSON → SQLite

> 记录"用什么存任务与推送数据"的决策。具体表结构在方案阶段另行设计,本文不写表。

## 决策:主存储用 SQLite

V1 用 `inbox.json` 通信,简单直接。但 V2 的需求(任务系统 + 推送历史)本质是**关系型数据**,继续用 JSON 是跟工具较劲:

| 维度 | JSON 文件 | SQLite |
|---|---|---|
| 查询/筛选 | 全量读进内存再过滤 | SQL 一句(如"超过正常周期的 start 任务") |
| 推送历史 | 嵌套数组越陷越深 | 独立的推送流水记录,一对多自然表达 |
| 并发安全 | 引擎写 + 人手改易冲突 | 事务,天然安全 |
| 崩溃恢复 | 写一半断电可能损坏 | WAL 模式很稳 |
| 数据量 | 任务多了越来越慢 | 轻松应对 |

场景特点:单机、单进程、读写频率不高——SQLite 完全够,且比 JSON 更稳。

## 可读性:人能看的出口

用户是 Obsidian 重度用户,习惯直接看数据。SQLite 用 VSCode 插件即可查看;必要时 APP 可**定期导出一份只读的 Markdown/JSON 摘要**(如任务清单、催史),写进 vault,兼顾程序严谨与人眼直观。

## 与 Claude Code 的通信(独立于存储)

- **存储**(SQLite)是 APP 的内部实现,Claude Code 不直接读写。
- **通信**走 HTTP 接口(`io/server.py`):Claude Code / WebUI 经 `/api` 同步调用
  任务增删改查与规则配置(`core/actions.py` / `core/settings.py`)。
- 早期的 `inbox.json` / `commands.json` 文件信箱已于通知层重构删除,
  改为同步实时调用,不再异步轮询。
