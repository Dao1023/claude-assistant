# 任务系统

> 本文描述任务模型的**设计思路**与**生命周期**。完整需求见 [requirements.md](requirements.md);表结构见 [schema.md](schema.md);存储选型见 [storage.md](storage.md)。

## 设计思路:透过现象看本质

任务管理工具换了一个又一个——清单、日历、每日计划、四象限、GTD、看板——但剥掉外壳,所有「要做的事」只有两种:

- **越久越该做的**(start):体检、看朋友、关注某领域。没有硬截止,但拖得越久越不该。
- **越近越急迫的**(end / DDL):周五要交的方案、今晚截止的报名、原神每日。有明确截止点,过了就没了。

**Claude Assistant 把任务管理抽离成这两条最朴素的驱动**,重要性不由拍脑袋的优先级数字决定,而由**时间自然发酵**:拖得越久、离得越近,就越无法忽视。

它**不是替你思考,是替 Claude Code 盯着你**:Claude 一关窗口就失忆,它在托盘里记住这些该做的事,到点把你拽回对话。助手,不是替代。

## 两种驱动,两个公式

时间与周期内部一律 **Unix 秒级整数**,start / end 都按秒算,精度统一。

| | start 驱动 | end 驱动(DDL) |
|---|---|---|
| 本质 | 越久没做越重要 | 越近截止越急 |
| 公式 | `log((now - anchor) / expected_duration)` | `-log((deadline - now) / 86400)` |
| 字段 | `anchor` + `expected_duration` + `is_cyclic` | `deadline` + `recurrence_interval` |
| 过期 | 不会"没了",只会越来越该做 | 过了就 closed(超时即结束) |
| 例 | 看朋友、体检、旅游、突发奇想 | 项目交付、原神每日、火车 16:25 |

### start:`log(距上次 / 预期间隔)`
- `x = (now - anchor) / expected_duration`,重要性 = `log(x)`。
- `x=1`(刚到预期间隔)→ 0,该做但不急;`x<1` → 负,排后面;`x>1` → 缓慢上升。
- 用 `expected_duration`(**预期间隔**)归一化,长周期任务(体检一年)不会因"最久"霸榜。
- 刚建/刚做完时 `x` 是 0~1 小数,`log(x)` 是**有限负数**自然排最后。

### end:`-log(剩余)`
- 剩余越少值越大。剩 30 天 → -3.4;剩 1 天 → 0;剩 0.1 天 → +2.3。
- **过了 deadline 就 closed,不再催**——没有"过期还狂催"这种状态。

## 字段级拆分:start 和 end 各填各的

早期用一个 `cycle_days` 身兼两职(start 的归一化分母 + end 的克隆间隔),还得「传了就自动当周期」,导致一次性的论文/项目任务被误标成周期、完成时错误克隆。

现在**字段级拆开**,start 和 end 各有专属字段、专属克隆逻辑、专属超时语义:

### start 三字段(互相独立)
- **`anchor`**:上次完成的时间戳(新任务 = 创建时)。做完了重置为 now,重新计时。
- **`expected_duration`**:预期间隔(秒),只用于重要性归一化,**不代表周期**。
- **`is_cyclic`**:完成后是否重置一个。独立开关——填了 `expected_duration` **不会**自动变周期。
  - 见朋友:`is_cyclic=1`,做完立即重置下一个。
  - 读某篇论文:`is_cyclic=0`,做完就消失(它带来结论,不是再读一遍)。

### end 两字段
- **`deadline`**:截止时间戳。
- **`recurrence_interval`**:重复间隔(秒),**空 = 非周期**。是否重复看它是否存在,不需要 is_cyclic。
  - 原神每日:`deadline=次日 4:00` + `recurrence_interval=1 天`。

## 生命周期:三状态

```
                        完成 ──────────►  done(真完成)
                       │
新建 ──► active ───────┤
        (唯一会被催)    │  手动关闭 ────►  closed ┐
                       └  超时(过 deadline) ►  closed ┴── 结束
```

| 状态 | 含义 | 引擎还算/还催吗 |
|---|---|---|
| **active** | 进行中 | ✅ 算重要性、会被催 |
| **done** | **真正完成**(只有它代表"做成") | ❌ 终态 |
| **closed** | **结束**:手动关闭 或 **超时自动结束** | ❌ 终态 |

### 为什么保留 done 和 closed 两个终态
代码层面它们行为一致(都不催)。保留两个是为**统计**:项目成功率 = `done / (done + closed)`。done 是"真完成",closed 是"结束了"(含没做完就到期的)。

### 超时即 closed
- end 任务**过了 deadline 立即 closed,不再催**。结束了就是结束了——除非你先**延期**(改 deadline)让它保持 active,否则过即终结。
- start 任务**不会**因超时被关(它本来就没有"过期",只会越来越该做)。

### 周期任务的克隆
周期任务**每次完成/超时都克隆一个独立实例**——不合并。凭什么原神每日要合并、公司一年几百个任务就各自独立?每个周期就是一条独立任务,一视同仁。

| 驱动 | done 时 | 超时 closed 时 |
|---|---|---|
| start 周期(is_cyclic=1) | 克隆下一个,anchor=now | —(start 不超时) |
| end 周期(recurrence_interval 非空) | 克隆下一个,deadline 顺延 | closed 当前 + 克隆下一个 |

于是原神每日一年产生 365 条独立记录,`done` 的做了、`closed` 的漏了,**漏做率**可直接统计。

## 任务的核心属性(概念层)

- **内容**:标题、备注。
- **驱动**:start / end(创建时定死,不可改,避免脏数据)。
- **时间**:created、start 的 anchor、end 的 deadline。
- **间隔**:start 的 expected_duration(归一化)、end 的 recurrence_interval(重复)。
- **tag**:多个,用于筛选/过滤。
- **主观优先级**:与客观重要度加权(尚未实现加权)。
- **状态**:active / done / closed。

## 催办是通知层的事,不是任务层

「多久催一次」**不是任务的属性**。任务层只负责算「这事多重要」(importance);通知层(pusher)自己根据「重要性 + 距上次催多久 + 当前档位」决定此刻该不该弹。任务不带"提醒频率"字段。
