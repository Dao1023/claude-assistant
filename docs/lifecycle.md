# 任务生命周期与催促策略

V1 的死穴:提醒是"弹一下就完事",没有后续。V2 的核心就是给任务一套**完整生命周期**——任务不解决,就一直追,有节奏、有强度变化。

## 状态机

```
        pending(待办)
           │ 到达提醒时机
           ▼
        notified(已提醒)
           │ 用户没解决(没看到/想歇会/点掉没做)
           ▼
        nagging(催收中) ←──────────┐
           │ 隔一段时间再催          │ 一直没解决
           ▼                        │
        escalating(升级催) ─────────┘
           │ 逾期越久/越重要,间隔越短
           ▼
        crisis(危机,连环催)
           │
           ▼ 只有用户明确动作才退出:
        done(做了) / snoozed(稍后) / dismissed(不做了)
```

## 催促节奏(三档强度)

| 档位 | 触发 | 行为 |
|---|---|---|
| **温和 nagging** | 到点提醒后用户未解决 | 随机间隔再催(如 1-3 小时随机一次),保持存在感但不烦 |
| **升级 escalating** | 逾期时间增长 / nag_count 累积 | 间隔逐渐缩短,频率上升 |
| **危机 crisis** | 逼近 deadline 或拖太久 | **夺命连环催**:一次连发 5-10 个弹窗,逼用户处理 |

**退出条件**:只有用户明确标记 `done` / `snoozed` / `dismissed` 才停止。"看了没点""点了没做"都不算解决。

## 防过载节流(关键)

任务多了会"催死用户",必须有节流:

1. **同时催促上限**:同一时刻最多同时催 **N 个**任务(建议 N=3),其余按重要度排队。
2. **重要度排序**:只有当前最该催的 N 个占用弹窗名额(重要度算法见 task-system.md)。
3. **全局静音**:用户可一键"今天别催了",暂停所有催促。

## 待用户拍板的参数

以下"度"直接影响被烦的程度,开发前需确定:

1. **同时最多催几个?**(建议 3 个)
2. **危机连环催一次连发几个?**(5-10 之间定个数)
3. **温和 → 危机的升级标准?**(按逾期时间?还是按 nag_count 次数?)
4. **温和期随机间隔范围?**(建议 1-3 小时)

> 这些先填进 protocols.md 的默认配置,体验一段时间后再调。
