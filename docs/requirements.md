# 需求:任务类型、重要性与推送策略

> 本文档只记录**需求与思路**(用户 2026-07-27 的原始思考,经讨论收敛),不写具体技术方案/表结构。
> 方案在需求确认后另行设计。

## 一、任务只有两类驱动方式

所有任务本质上只有两种**驱动方式**:

### 1. start 驱动(启动时间)
- 持续时间越长,重要性越大,呈**对数增长**。
- 例:1天、2天、4天、一周、2周、1月、2月、1季度、2季度、一年……每次增长都是对数的。
- 任何"觉得我好久没做了"的事都属此类:很久不见的朋友/家人、体检、旅游、好几年没关注的领域、突发奇想想做的东西。

### 2. end 驱动(DDL)
- 有**固定结束时间**,时间不等人,过了就没了。
- 例:原神每日、公司项目交付、今天火车 16:25。

## 二、周期任务 = 周期的 start 或 end

周期**不是独立的驱动方式**,而是叠加在 start / end 上的修饰符:

- **周期 end**:今天原神每日,明天也要每日;周本同理。到点"过期",做完明天生成新的。
- **周期 start**:今天见了朋友,约定以后几个月再来——这是一个 start 任务,结束后下次还要再聚(锚点重置)。

**实现方式**:只需标记任务"是否周期"。一个周期任务**完成后,系统自动创建一模一样的下一个任务**,除非某天这件事彻底结束(手动关闭)。

## 三、重要性算法(用 log)

两种驱动是一对镜像,对数是它们的天然形状。

### start:`log(发生以来时间 / 正常周期)`
- 设 `x = 距上次时间 / 正常周期`,重要性 = `log(x)`。
- `x = 1`(刚到正常周期)→ log(1) = 0,重要性为零:到点了该做,但还不急。
- `x > 1`(拖了)→ 重要性缓慢上升;`x < 1`(还没到)→ 重要性为负,不排上号。
- **作用**:归一化。体检(周期约一年)和看朋友(周期约一月)能在同一把尺子下比较——体检不会因为"最久"就永远霸占前排。
- 因此 start 任务需要一个"**正常周期**"(预期间隔)字段,不是结束时间,专门用于归一化。

### end:`-log(剩余时间)`
- 剩余时间越少,值越大(越近越急)。
  - 剩 30 天 → -log(30) = -3.4(不急);剩 1 天 → 0;剩 0.1 天 → +2.3(很急)。
- **边界**:剩余时间 → 0 时值 → +∞。工程上要处理"已过期"(剩余 ≤ 0)的情况,可设为一个很大的固定值,表示"已错过,最高优先"。

## 四、任务打 tag

- 任务可以打 tag,用于**筛选 / 过滤**。
- 动机:避免"心血来潮加了 10 个原神任务,导致其他任务找不到"——可按 tag 筛出或隐藏某一类。

## 五、推送层(与任务层独立)

- 推送层与任务层**相互独立**。
- 推送层扫描"今天要干什么",列出:
  - **end 清单**:按结束时间排序。
  - **start 清单**:按**重要性算法**排序(不是纯按时长,否则会霸榜,见上)。
- 推送层对每个具体任务**保留其推送生命周期**:推了很久就增加推送频率,但**始终是这同一个任务**,不是别的。
- 周期任务克隆出新任务时,推送计数随之重置(新任务还没被催过)。
