# 架构与职责边界

## 总体架构

```
┌─────────────────────────────────────────────────────────┐
│  Claude Code(大脑)                                    │
│  - 理解自然语言("最近要搞 XX""XX 做完了")              │
│  - 做决策、与用户对话、读取 vault                          │
│  - 把"要记的事"翻译成结构化指令,写进 inbox.json          │
└──────────────────────┬──────────────────────────────────┘
                       │ inbox.json(指令:增/删/改)
                       ↓
┌─────────────────────────────────────────────────────────┐
│  常驻 APP(任务系统 + 生命周期引擎)                     │
│  - 解析 inbox.json 指令,维护 tasks.json 任务库          │
│  - 增删改查、筛选、按重要性模型计算当前该催谁            │
│  - 跑任务生命周期:定时检查、催促、升级、节流            │
│  - 弹系统通知,唤起 claude(cwd=Obsidian 库,免确认)      │
│  - 回写状态供 Claude Code 查询                           │
└──────────────────────┬──────────────────────────────────┘
                       │ 系统通知(带生命周期、可连环催)
                       ↓
                      用户
```

## 职责划分原则

| 维度 | 归 Claude Code | 归 APP |
|---|---|---|
| 本质 | 概率性的、需要理解和判断的 | 确定性的、批处理的 |
| 典型事 | 听懂"朋友很久没看了"是什么意思 | 算出"哪些朋友超过 N 天没联系" |
| 数据 | 不持有任务库,随用随取 | 持有 tasks.json,权威数据源 |
| 触发 | 用户主动唤起 / APP 唤起 | 常驻,自主定时跑 |

**一句话:Claude Code 负责"理解",APP 负责"记住 + 追到底"。**

## 为什么 APP 要持有任务库(而不是 Claude Code)

- **上下文成本**:任务多了,Claude Code 每次对话全量读取,慢且贵。
- **可靠性**:程序筛选零遗漏;模型可能漏、可能记串。
- **可复用**:筛选逻辑(按时间/类型/重要度过滤)写一次,永久稳定复用。
- **常驻性**:生命周期引擎需要 7×24 定时跑,Claude Code 不可能常驻。

## 不变的部分(V1 已验证)

- 唤起方式:`subprocess` + `cmd /c start` 启动 `claude.exe`,`cwd` 设为 `C:\Obsidian`,免信任确认。
- 唤起后**不默认塞对话**:新窗口是无记忆的新会话,只打开干净窗口,用户自己 `/resume` 并说明"是助手提醒我来找你"。短期不让 APP 侵入会话上下文。
- 托盘常驻(pystray)+ 系统通知(windows-toasts)。
