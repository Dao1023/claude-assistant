# 架构与职责边界

## 总体架构(四层)

```
①事件层   core/engine, actions     任务、截止时间、用户点击产生事实
②通知层   io/pusher, core/funnel   挑谁、催几次、什么档(确定性判断)
③弹窗层   io/notify_window,/notify 被动渲染通知层结果 + 收集用户回应
④AI 层    io/agent(规划中)        旁观 ①②③ 的事件流,自主决定沉默或开口
```

层与层靠**单向数据流 + 一条事件总线**解耦:

```
①②③ 发生的事 ──publish──>  io/events.py 事件中枢(/ws WebSocket 总线)
                                │  订阅者各取所需,互不依赖
              ┌─────────────────┼─────────────────┐
              ↓                 ↓                 ↓
          ③浮窗渲染         ④AI 旁观          (未来)日志/统计
```

**为什么这样切:** 每层可独立测试、可替换。通知层决定"弹了",把结果推上总线;
弹窗层被动接收、不主动查询;AI 层只读总线 + 历史,**不改前三层**,想说也是
推一个 `ai_message` 事件回总线,浮窗被动渲染气泡。

| 层 | 本质 | 概率/确定 |
|---|---|---|
| ①②③ | 确定性的、批处理的、要可靠的 | 确定性(代码) |
| ④ AI | 概率性的、需要理解和判断的 | 概率性(模型) |

**一句话:前三层负责"记住 + 追到底",AI 层负责"看懂 + 点到为止"。**

## 职责划分原则

| 维度 | 归 AI 层 | 归前三层 |
|---|---|---|
| 本质 | 概率性的、需要理解和判断的 | 确定性的、批处理的 |
| 典型事 | "这人连推 3 次还说在开会,是真忙还是偷懒" | "这个任务超过 N 天没做,该催第几档" |
| 数据 | 不持有任务库,只读总线 + 历史 | 持有 SQLite,权威数据源 |
| 触发 | 常驻旁观,自主决策 | 常驻,定时/事件驱动 |
| 模型 | 可插拔 LLM(便宜云 API / 本地) | 无 |

## 前后端边界:数据 vs 解释

APP 内部还有一条更细的边界——**core 层(后端逻辑)与前端(WebUI)之间**。
判据不是"后端=纯数据"一刀切,而是看这段文字描述的是**客观数据**还是**后端的判断逻辑**:

| | 数据(归后端纯给) | 解释(逻辑自带说明书) |
|---|---|---|
| 是什么 | 客观存在的字段:deadline、anchor、importance | "为什么这任务现在不催"——对一段判断逻辑的翻译 |
| 文案在哪 | **前端**拼(倒计时、X 天没做了) | **后端**拼(funnel 每层的 reason) |
| 为什么 | 视图可多样,数据要纯净;前端还能做实时倒数 | 解释必须和判断逻辑同源,否则逻辑改了文案没跟上,页面开始骗人 |

**为什么 reason 留在后端、不拆成结构化数据给前端拼:**
规则页的全部价值在于"展示 = 真实运行",用户信它。reason 和判断逻辑物理上住在同一个函数里,
改逻辑时顺手就改了文案,想不同步都难。若拆给前端,后端逻辑一变、前端模板还在用旧字段拼,
两者脱节——而规则页最不能失去的就是"它没骗我"。代价(改措辞要重启后端)很小且一次性,
换来的是逻辑与解释永不脱节。

**落地实例:**
- ✅ 倒计时:后端只给 `deadline` 时间串,前端 `endFooter` 自算"还剩 X 天/已过期"(曾 `_fmt_countdown` 在后端拼,已删)。
- ✅ funnel reason:后端纯函数生成"已过 X / 冷却 Y = 间隔 Z × 系数 W",前端直接渲染——这是逻辑的解释,不动。

**一句话:后端给数据时是纯的;后端给解释时,解释和逻辑绑死。**

## 任务模型(双驱动)

任务系统围绕两类驱动组织(详见 [task-system.md](task-system.md)):

- **start 驱动**:越久没做越重要,`log(发生以来/正常周期)`。
- **end 驱动(DDL)**:越近截止越急,`-log(剩余时间)`,过期即失。
- **周期**是叠加在 start/end 上的修饰符,完成后自动克隆下一个。

存储用 **SQLite**(见 [storage.md](storage.md))。前端面板与催办浮窗复用同一套
Vue 前端,走 FastAPI REST + WebSocket。

## 为什么 APP 要持有任务库(而不是 AI)

- **上下文成本**:任务多了,模型每次全量读取,慢且贵。
- **可靠性**:程序筛选零遗漏;模型可能漏、可能记串。
- **可复用**:筛选逻辑(按时间/类型/重要度过滤)写一次,永久稳定复用。
- **常驻性**:生命周期引擎需要 7×24 定时跑,模型不该扛这个。

## 推送出口(浮窗)

唯一推送出口是 **pywebview 无框置顶浮窗**(`io/notify_window.py`),内容是
FastAPI 托管的 `/notify` 页(复用面板 Vue 前端)。常驻单例:启动建 hidden 窗,
通知 show、用户点 × 隐藏不销毁。按钮(完成/推迟/留言/全部稍后)走已测 REST API。
托盘菜单「显示待办窗」可随时手动唤出。

(原 tkinter 小卡已删除:手写坐标布局易碎、丑、交互弱。)

## AI 层(规划中)

第四层,一个**常驻旁观的 Agent**,不是聊天框。设计要点:

- **感官**:订阅 `/ws` 总线(与浮窗同一条),收 `notify / done / snooze / dnd`
  事件;另可只读 `push_log`(含用户留言)与任务 REST API 补历史上下文。
- **大脑**:可插拔 `LLMBackend` 抽象,第一实现接 **DeepSeek 等便宜云 API**
  (OpenAI 兼容,`base_url + key` 可配,换家只改配置);本地 LM Studio 留作备用;
  `Mock` 实现供测试不调真模型。
- **判断**:`should_speak(context) -> None | str`,大多数时候沉默,攒够
  "这人不对劲"的信号(连推 N 次、长时间不动)才开口。用户留言是判断
  "真忙 vs 偷懒"的关键证据。
- **嘴巴**:推一个 `ai_message` 事件回总线,浮窗渲染气泡;用户在浮窗输入框
  回答,POST 回 AI。

**原则:AI 只旁观 + 经开放通道反向说话,绝不改前三层。AI 烂了,前三层照常工作。**

### Roadmap

第四层分阶段落地,每步独立可测、可交付:

- [ ] **A. 抽象 + 管道**:`LLMBackend` 接口 + `Mock` 实现;`Agent` 常驻线程订阅
  总线攒上下文。先把"旁观 → 判断 → 说话"管道打通,不接真模型。
- [ ] **B. 事件 + UI**:总线加 `ai_message` 事件类型;浮窗加气泡 + 输入框。
  跑通"推迟 3 次 → 气泡冒一句『这个卡了三回了,是遇到什么坎了吗?』"。
- [ ] **C. 接真模型**:`CloudAPI(base_url, key)` 实现,接 DeepSeek;配置化切换。
- [ ] **D. 记忆与上下文管理**:跨会话记住用户习惯/借口,Agent 自主管理上下文窗口。
- [ ] **E. 更主动**:每日复盘、主动规划、识别长期模式(周报式洞察)。
